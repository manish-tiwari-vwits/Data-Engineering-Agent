GRAVITY-3335 Colibri Staging to Split Core Model

Prepared from .synapse_work/Fact_ColibriWorkItems.sql, .synapse_work/Dim_ColibriProducts.sql, .synapse_work/Dim_ColibriUsers.sql, available BIA draft placeholders, and the existing broad model inventory in docs/GRAVITY-3335-colibri-core-data-model.html. Date: 2026-09-27.

1. Executive Summary

The current core table dwh_core.Fact_ColibriWorkItems is doing too much: it acts as the work item identity table while also carrying BIA and finance impact, risk, release, budget, hierarchy, user-role, date, and audit attributes. This makes the core model wide, hard to govern, and difficult to extend when different subject areas evolve at different grains.

The proposed target is a split core model loaded from dwh_staging.COLIBRI_WORKITEMS. dwh_core.Fact_ColibriWorkItems becomes the work item hub with only identity and common descriptors. Subject-specific facts hold BIA/finance, risk, release, and budget attributes. Bridges hold parent-child hierarchy and user-role relationships. Existing dwh_core.Dim_ColibriProducts and dwh_core.Dim_ColibriUsers remain shared dimensions joined by stable surrogate keys.

Source caveat: .synapse_work/Fact_ColibriWorkItemBIA.sql and .synapse_work/p_stg2core_LOAD_Fact_ColibriWorkItemBIA.sql currently contain placeholder-only draft text in this workspace. The BIA placement and visible mapping notes below therefore use the existing broad documentation matrix as reference where executable BIA draft SQL is not available.

3. Existing Core Issue

dwh_core.Fact_ColibriWorkItems currently contains the work item hub plus multiple subject domains in one wide table. It includes identity, product, parent hierarchy, generic descriptors, risk, release, budget, BIA/finance, user-role, lifecycle date, data quality, and ETL audit columns. This causes subject-area coupling: a BIA change can affect the work item hub, release and budget measures sit beside unrelated classification fields, and user-role relationships are compressed into columns instead of modeled as repeatable roles.

The split model keeps the current stable keys but assigns each column family to a smaller table with a clear grain and ownership boundary.

7. Plain-Language Join Explanation

WorkItemId is the original source ID from Colibri. It is the ID business users may recognize from the operational system. In core, that same value is stored as COLIBRI_WORKITEM_BK, where BK means business key: the source-facing identifier.

COLIBRI_WORKITEM_SK is the internal warehouse ID. It is created so the warehouse can join tables reliably, even when source IDs are long, inconsistent, or need historical handling. Most core joins should use COLIBRI_WORKITEM_SK, not the source WorkItemId.

Products follow a similar two-step path. The staging table provides ProjectId. That value matches Dim_ColibriProducts.COLIBRI_PRODUCT_BK. The product dimension then gives the internal COLIBRI_PRODUCT_SK, which is stored on the hub and can also be copied to subject facts where it makes reporting simpler.

The subject facts are like topic folders for the same work item. The hub says, "this is the work item." The BIA fact says, "these are the BIA and impact details for that work item." The risk fact says, "these are the risk details for that work item." Release and budget work the same way. All of them tie back to the same work item by COLIBRI_WORKITEM_SK.

Bridges are used when a work item can have relationships rather than just one fixed value. A parent-child relationship needs a hierarchy bridge because one work item can point to another work item. User roles need a user-role bridge because one work item can have many different people or organizations attached to it, such as responsible person, stand-in, changed-by user, BIA responsible IT, or BIA manager business.

FROM dwh_core.Fact_ColibriWorkItemBIA bia

  ON hub.COLIBRI_WORKITEM_SK = bia.COLIBRI_WORKITEM_SK

  ON prd.COLIBRI_PRODUCT_SK = COALESCE(bia.COLIBRI_PRODUCT_SK, hub.COLIBRI_PRODUCT_SK)

  AND bia.COLIBRI_CLASSIFICATION_TYPE = 'BIA-IT'

  ON prd.COLIBRI_PRODUCT_SK = hub.COLIBRI_PRODUCT_SK

Parent-Child Join

FROM dwh_core.Bridge_ColibriWorkItemHierarchy h
JOIN dwh_core.Fact_ColibriWorkItems child
  ON child.COLIBRI_WORKITEM_SK = h.COLIBRI_WORKITEM_SK
LEFT JOIN dwh_core.Fact_ColibriWorkItems parent
  ON parent.COLIBRI_WORKITEM_SK = h.PARENT_COLIBRI_WORKITEM_SK

User Role Join

FROM dwh_core.Bridge_ColibriWorkItemUserRole role_bridge
JOIN dwh_core.Fact_ColibriWorkItems hub
  ON hub.COLIBRI_WORKITEM_SK = role_bridge.COLIBRI_WORKITEM_SK
LEFT JOIN dwh_core.Dim_ColibriUsers usr
  ON usr.COLIBRI_USER_SK = role_bridge.COLIBRI_USER_SK
WHERE role_bridge.ROLE_CODE IN ('RESPONSIBLE', 'OWNER', 'STANDIN', 'CHANGED_BY', 'BIA_RESPONSIBLE_IT', 'BIA_RESPONSIBLE_BUSINESS')
