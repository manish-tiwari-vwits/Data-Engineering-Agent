GRAVITY-3335 Colibri Core Data Model

Prepared from editable Synapse draft files in .synapse_work/ and staging artifact synapse_artifacts/sqlscript/COLIBRI_WORKITEMS.json. Date: 2026-09-27.

Scope

This document describes the recommended core model for Colibri work item data, with emphasis on splitting the current wide dwh_core.Fact_ColibriWorkItems table into a central work item hub plus subject facts for BIA, risk, release, budget, hierarchy, and user-role relationships.

  • Inventories every column from .synapse_work/Fact_ColibriWorkItems.sql and .synapse_work/Fact_ColibriWorkItemBIA.sql.
  • Documents the current BIA load mapping from dwh_staging.COLIBRI_WORKITEMS as visible in .synapse_work/p_stg2core_LOAD_Fact_ColibriWorkItemBIA.sql.
  • Documents the existing reporting view draft .synapse_work/V_COLIBRI_WorkItems_BIA.sql and existing dimensions Dim_ColibriProducts and Dim_ColibriUsers.

Assumptions

  • The current Synapse staging source for the BIA procedure is dwh_staging.COLIBRI_WORKITEMS.
  • The current business key for a work item is WorkItemId, loaded as COLIBRI_WORKITEM_BK.
  • ProjectId links to dwh_core.Dim_ColibriProducts.COLIBRI_PRODUCT_BK and produces COLIBRI_PRODUCT_SK.
  • User fields that are already SK-like should be aligned to dwh_core.Dim_ColibriUsers where a stable user business key is confirmed.
  • The proposed Risk, Release, Budget, Hierarchy, and UserRole tables require physical DDL approval before implementation.

The visible model below is designed for Confluence paste: staging lands once, the hub owns work item identity, subject tables own domain-specific attributes, bridges own many-valued relationships, and reporting views join the split tables back through stable surrogate keys.

Reporting Join Example

SELECT
  bia.COLIBRI_WORKITEM_TYPE AS WorkItemType,
  bia.COLIBRI_CLASSIFICATION_TYPE AS Custom_gdpfClassificationType,
  bia.COLIBRI_LAST_REVIEW_DateTime AS ReviewLast,
  bia.COLIBRI_BIAIT_SCORE AS Score,
  bia.COLIBRI_CALCULATED_BUSINESS_IMPACT AS BIA_Result,
  prd.COLIBRI_PRODUCT_BK AS ProjectId
FROM dwh_core.Fact_ColibriWorkItemBIA bia
LEFT JOIN dwh_core.Fact_ColibriWorkItems hub
  ON hub.COLIBRI_WORKITEM_SK = bia.COLIBRI_WORKITEM_SK
LEFT JOIN dwh_core.Dim_ColibriProducts prd
  ON prd.COLIBRI_PRODUCT_SK = COALESCE(bia.COLIBRI_PRODUCT_SK, hub.COLIBRI_PRODUCT_SK)
WHERE bia.COLIBRI_WORKITEM_TYPE = 'Classification'
  AND bia.COLIBRI_CLASSIFICATION_TYPE = 'BIA-IT';

Validation Checklist

  • No skipped columns: reconcile 126 wide fact columns, 71 BIA draft columns, and 129 unique disposition rows in this document.
  • Row count checks: compare old wide-fact BIA-filtered rows to new BIA subject rows for Classification and BIA-IT.
  • Duplicate BK checks: enforce one row per COLIBRI_WORKITEM_BK in BIA subject fact unless source grain is intentionally changed.
  • Join orphan checks: BIA rows without hub SK, product SK, or required user dimension matches should be counted and reviewed.
  • Old vs new BIA view reconciliation: compare each reporting alias in V_COLIBRI_WorkItems_BIA from old wide fact versus new BIA fact plus joins.
  • Checksum/update path checks: verify every persisted BIA attribute appears in insert, update, ROW_CHECKSUM, and ROW_CHECKSUM_EXCL_KEYS paths.
  • Watermark/dedupe checks: confirm latest _lineage_row_id per WorkItemId is used and source watermark bounds are respected.

Implementation Sequence

  1. Create new subject tables additively: BIA first, then Risk, Release, Budget, Hierarchy bridge, and UserRole bridge after ownership approval.
  2. Load subject facts from dwh_staging.COLIBRI_WORKITEMS using the existing hub and dimensions for lookup keys.
  3. Run reconciliation checks against current Fact_ColibriWorkItems and the current BIA reporting view.
  4. Update V_COLIBRI_WorkItems_BIA to read BIA attributes from Fact_ColibriWorkItemBIA and shared descriptors from hub/product joins.
  5. Optionally slim the wide fact only after reporting consumers migrate and reconciliation remains stable.
